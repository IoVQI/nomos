# Version Registry — 版本策略与注册表

> **作用**：版本信息的单一入口。
> **受众**：AI 助手、项目维护者

---

## 一、策略

本骨架**不采用文件级版本号**。经验教训（来自本骨架的原始项目）：

> 🔴 **工作流文件级的 `wf-X.Y` 版本号与配套的计数桶，最终全部退役。**
> 原因：它们不驱动任何行为、不参与任何闸门判定，却需要每次改动手工同步 N 处；
> 一旦漏同步就产生「文档声称的版本 ≠ 实际内容」的漂移，而**没有任何机制能发现这种漂移**。
> 这正是 §计数描述退役原则 要消灭的东西——**会漂的手写投影**。

**替代方案**：

| 需求 | 用什么 |
|------|--------|
| 「这份文件什么时候改的」 | frontmatter 的 `last_updated`（写文件时现场取钟） |
| 「改了什么」 | `git log <path>` —— **版本真源是 git，不是文档** |
| 「整体处于什么阶段」 | git tag（人工决策） |
| 「某设施是否还存在」 | 现场实盘（`ls` / 各注册表实盘），不在文档里写死 |

## 二、注册表

| 范围 | 版本 | 备注 |
|------|:----:|------|
| 整个骨架 | 见根目录 [`VERSION`](../VERSION) | **单一真源**；发布时由 `VERSION` 与 git tag 共同承载 |

**不再维护**：组件级版本桶、文档清单计数、frontmatter 覆盖率统计、
以及任何重复的版本号副本——它们都属「会漂的手写投影」。

## 三、闸门

版本相关**没有任何自动闸门**（原 `check_workflows.py` 的 G3/G4/G9 计数对账已退役）。
这不是缺口：没有可机械判定的规则，就不该有假闸门。
