# parallel_session_launch_workflow — 并行会话启动建议（触发器层）

> **作用**：回答「**该不该并行**」，并在判定为「该」时**按执行载体**产出方案或直接派单（判据见 §2.3 / Phase 5）。
> **它不是什么**：不执行并行（执行协议是 `sandbox/_parallel/README.md`）；不做交接（`sandbox/_handoff/README.md`）。
> **位置**：并行 / 串行协议的**上游触发器**——两份 README 的消费点都写在「用户已经决定之后」，本工作流补上那个决定。

## 工作流目标

统一「要不要开并行会话」的准入判断，确保：

- **判据可查**：以「宽 + 写域不相交 + 够长/阻塞等待」三条件替代主观感觉
- **产物按载体分路**：丙档（独立会话）产出预填提示词，用户只做核对 + 粘贴；甲/乙档（子代理 / teammates）**直接派单**，不产提示词（§2.3 / Phase 5）
- **有否决路径**：「不必并行」与「先澄清」是第一等输出，不是兜底
- **可退役**：自带退役判据与留痕口径（`project/standards/06` §2-5）

**核心原则**：

- **两段式**：先**分解**（价值所在），再判**可并行**。歧义不是并行理由——歧义的正解是澄清或会话内子代理侦察（协调成本为零）。
- **拓扑是推导结果**：由写域图决定网状 / 树状 / 混合，不是自由选择。
- **协调成本入账**：成本主体**随载体而变**（甲/乙档 = 本会话的上下文与监督开销；丙档 = **用户**开 N 个窗口、来回贴提示词），单条工作流过短则不摊薄成本（判据见 §2.3）。
- **不重复规则**：判据与三态出口的真源在本工作流；`sandbox/_parallel/README.md` §6 只留导航，不复制规则（防第二真源）。

## 适用场景

- 用户给出**宽泛/广域**指令（如「项目里有点乱」「把 X 领域推进一下」），可能拆成多条独立工作流
- 会话结束时仍**有可分派**的剩余工作（`.claude/commands/闭环本会话.md` §4.5 的出口；2026-09-17 由 `chain_orchestration_workflow.md` Phase 0d-8 移交）
- 主线**卡在慢 I/O**（MinerU 转录 / CI / 长 solver 扫描 / 批量下载），跨等待并行有明确净收益

## 不适用场景

- 单一工作流（拆不出 ≥2 条候选）→ 直接做，或用会话内子代理
- 纯只读会话（调研 / 审计不落盘）→ `sandbox/_parallel/README.md` §6 已列
- 已用任务卡把写入域天然隔开（如 case-a 订阅卡：一人一篇笔记）→ 用那套即可

## Phase 0 — 输入解析

**两个触发时机**（互不替代）：

| 时机 | 入口 | 输入 |
|---|---|---|
| 会话中途 | Skill 入口 `parallel-session-check`（用户给出宽泛 / 广域指令时加载，或用户显式询问该不该并行） | 「用户原话 + 当前会话已认领的工作」 |
| 会话结束 | `.claude/commands/闭环本会话.md` §4.5（2026-09-17 由 `chain_orchestration_workflow.md` Phase 0d-8 移交） | 「本会话已完成工作 + 未提交文件 + 剩余待办」 |

> 🔴 **「会话中途」行原是无挂载点的（2026-09-17 补）**：本工作流建成（2026-09-15）后，该时机全库引用
> 只有**注册行 / 导航 / 消费者侧**——最近的 CLAUDE.md 指针嵌在 §沙箱会话间传递 中「**我已被指派为并行会话**
> 时该做什么」那一行的句尾，读到它时决策已发生。⇒ 该时机**静默零运行**（实证：至 2026-09-17 使用记录无新增行）。
>
> 补法**不是再加一条文本提醒**——`project/standards/06` §1 第 4 问（手段问）已把「把文档再写全一点以防遗忘」
> 列入默认拒绝清单。补的是一个**必然加载的载体**：Skill 的 `description` 每次会话都进上下文，
> 且靠**描述匹配**触发而非「AI 该记得」。相关规则仍以本工作流为唯一真源，Skill 只做入口与工具预授权。

**输入契约**：

```
{
  请求或剩余工作,        # 原文，不改写
  用户可用窗口数,         # 1 / N / 未知（未知按 1 处理——不可假设用户能开多窗口）
  是否已有对等会话        # ListAgents 结果（⚠️ 只答「谁在线」，不答「在做什么」）
}
```

**退出条件**：三个字段均有值（未知须显式写「未知」，不得留空）。

## Phase 1 — 分解

把输入拆为 N 个**候选工作流**，每个候选给出**四要素**（缺一即不完整）：

| 要素 | 说明 |
|---|---|
| `slug` | kebab-case 标识，用作 `sandbox/_parallel/claims/<today>_<slug>.md` 文件名 |
| `写入域` | 该候选会写的**全部**路径——🔴 **必须含产出去向目录**，不只源码路径（`sandbox/_parallel/README.md` 铁律 2 实证） |
| `产出` | 一句话说清改完/做完后世界里会多出什么 |
| `验收判据` | 可验证的判据，一句话写得出来 |

### 🔴 闸门 P1-G1（派单门）

```
任一候选写不出「验收判据」 ⇒ 该候选不派：并入主线，或退回用户澄清。
```

验收判据写不出来的批次，即使拆开了也无从验收——派出去只会产生无法收口的工作。

**退出条件**：候选清单齐备，或明确「候选数 < 2 → 转 Phase 3 输出 B 态」。

## Phase 2 — 可并行判据

### 2.1 四条件

| 代号 | 条件 | 判据 |
|:---:|---|---|
| C1 | **宽** | 候选数 ≥ 2 |
| C2 | **写域不相交** | 候选之间（**含共享层**）两两无交叠 |
| C3 | **够长** | 单条工作流长到能摊薄协调成本（见 2.3 时长下限） |
| C4 | **阻塞等待** | 主线卡在慢 I/O（转录 / CI / 长扫描 / 批量下载） |

### 2.2 判定式

```
可并行 = C2 ∧ (C3 ∨ C4)     且前置 C1 成立
```

- **C1 不成立** → 直接输出 B 态，不进入后续 Phase。
- **C2 是承重项**。写域交叠**不是「小心一点就行」**——`sandbox/_parallel/README.md` §1 六行实证全部来自交叠写入域。
- **C4 是最干净的收益**：跨的是**等待**，不是工作量。

### 2.3 协调成本与执行载体（时长下限）

并行**不是只有一种执行方式**。载体不同，成本主体就不同——2026-09-17 实测
（真源：`sandbox/_parallel/claims/2026-09-17_psl-skill-entry.md`）：

| 载体 | 谁执行 | 成本主体 | 实测约束 |
|:---:|---|---|---|
| **甲 · 会话内子代理** | 本会话派 `Agent`（**不带** `name`，或带 `isolation`） | 本会话**上下文预算** | 结果回到本会话上下文；**报告不直接给用户**（须由本会话转述）；有 usage 可核算 |
| **乙 · teammates** | 本会话派 `Agent`（**带** `name`，需 agent teams 开关） | 本会话**监督开销** | 🔴 长结构化回传**会被截断**；**不提供 usage**（成本不可核算）；跑在主会话工作目录 ⇒ 写域仍须显式分配 |
| **丙 · 独立会话** | 用户开窗口 + 粘提示词 | **用户窗口成本**（开 N 窗、来回贴、分散注意力） | 唯一**用户可见 / 可介入 / 可跨本会话存活**的载体 |

**载体选择判据**（先定载体，再谈时长）：

- 需要**用户看见 / 用户中途判断 / 跨本会话存活** → **丙**
- 长任务且**必须落盘即安全**（子代理生命周期短于会话）→ 优先 **丙**；仍选甲/乙时，任务书须要求**每步落盘**
- **大批量结构化采集** → **甲** 或 `.js` 工作流（乙会截断，见上表实测）
- 需要独立上下文但**不需要用户监督** → **乙**

**时长下限**：**单条工作流若短于一次检索式交互所能完成的范围，不提并行**——收益跑不过装配成本
（同 `CLAUDE.md` §不可逆操作确认原则的「回滚成本 > 确认成本」算法）。
⚠️ 装配成本**随载体不同**：丙档要人开窗口（最高）；甲/乙档近似为零 ⇒ **同一批候选在甲/乙档可能够长、在丙档不够长**，须按所选载体分别评估。

🔴 **不得因载体便利而放宽 C2**：写域不相交是三种载体**共同的硬前提**。「反正是我自己派的子代理，冲突了我来协调」不是理由——交叠写域的损害与载体无关（`sandbox/_parallel/README.md` §1 六行实证）。

### 2.4 🔴 反对信号（不得作为并行理由）

- 「任务描述很模糊」→ 歧义信号，正解是澄清或会话内子代理侦察
- 「感觉工作量大」→ 未分解的主观量感；须先过 Phase 1 得到候选数与写域
- 「多开几个会话总没坏处」→ 无净收益的纯开销

## Phase 3 — 三态输出

输出**必须**是三态之一，禁止裸输出「建议并行」而不给分解：

| 态 | 含义 | 后续 |
|:---:|---|---|
| **A** | 建议并行 N 路（**须同时定载体**，见 §2.3） | 进 Phase 4 → Phase 5（按载体分路产出） |
| **B** | 不必并行（会话内子代理即可） | 说明为何（命中 2.4 哪条），不产生任何文件 |
| **C** | 先澄清 | 用 `AskUserQuestion` 收敛歧义，回到 Phase 1 |

**B 与 C 是第一等输出**。一个见宽泛就喊并行的设施会变噪音、被忽略，然后孤儿化（实证：`update_chain_tracking.py` 孤儿化、`sandbox/_handoff/README.md` §7 警告）。

## Phase 4 — 拓扑推导

由写域图**推导**形状，不自由选择：

| 写域图 | 拓扑 | 适用 |
|---|---|---|
| 零共享产物 | **网状**（同权） | 仅任务卡模式（一人一篇 / 一人一个模型）——本仓库**例外** |
| ≥1 共享产物 | **树状**（有 leader） | 本仓库**默认**；leader 单写共享层 |
| 共享层 + 不相交簇 | **混合** | 共享层走树 + 簇内走网；>1 共享产物场景的现实答案 |

### 4.1 树状的两条必需规则

1. **leader 上下文预算**：树使 leader 成为聚合瓶颈。leader **要么只协调**，**要么只做一条工作流并把合并委派出去**——不得既做工作流又做合并。
2. **改判上报回路**：worker **可以在证据面前改判**（若照字面执行会改错文件 / 数值），但**必须说明**。此条有实证价值：2026-09-15 `memo-small-batch-cleanup` 辅助会话自主发现 2 处 memo 字面与实际不符 + 1 项模式级缺陷（真源：`sandbox/_parallel/_aux_session_prompt_template.md` §使用记录）。

### 4.2 两轴路由（写进预填提示词）

| 轴 | 取值 | 作用 |
|---|---|---|
| **路由轴** | 维护 / 科研 | 维护 → `records/index.md` §工作备忘录（AI 可写）；科研 → `project/research/index.md` §1（`writable_by: user`） |
| **可行性轴** | 共享层 / 域层 | 共享层写入串行化（leader 独占）；域层写入可并行 |

🔴 **科研分支硬约束**：科研台账 `writable_by: user` ⇒ **科研侧并行会话不能自行结项**，必须把逐条结项依据交回 leader / 用户。

## Phase 5 — 产物生成（按载体分路）

A 态下按选定载体分两路产出：

| 载体 | 产出 | 落点 |
|:---:|---|---|
| **丙 · 独立会话** | 按 `sandbox/_parallel/_aux_session_prompt_template.md` 产出**每候选一份**预填提示词 | 对话中，用户核对后粘贴 |
| **甲 / 乙 · 子代理 / teammates** | **直接派单**——不再产提示词；派单前写死四要素（`slug` / 写入域 / 产出 / 验收判据），并把「改判须说明」写进任务书（§4.1 第 2 条） | `Agent` 调用；结果由本会话**转述**给用户（甲/乙的报告不直接给用户） |

> 🔴 两路共同义务：§使用记录 留痕（§6.2）与 P1-G1（验收判据可写）**一律照旧**。
> 🔴 甲/乙档的「写入域不相交」由**本会话**在派单时显式分配——派单者全知，故**不需要** claim 做发现；
> 但**留痕仍要**：派单前后把各路写域清单记进 §使用记录（派单会话若中途退出，他人须能知道谁改了哪里）。

**丙档的四要素占位符**：

| 占位符 | 必填 | 来源 |
|---|:---:|---|
| `<slug>` | ✅ | Phase 1 |
| `<任务一句话>` | ✅ | Phase 1 |
| `<写入域清单>` | ✅ | Phase 1（含产出去向目录） |
| `<对应事项编号>` | 建议 | 两台账（维护 / 科研） |
| `<验收判据>` | 建议 | Phase 1（P1-G1 已保证可写） |

**收尾口径**：主 / 辅助会话的分工与收尾范围以 `sandbox/_parallel/README.md` §4 与 `.claude/commands/闭环本会话.md` §0.5 为准——本工作流不复制。

## Phase 6 — 退役判据与留痕

### 6.1 退役判据（`project/standards/06` §2-5 要求）

| 分支 | 判据 | 含义 |
|:---:|---|---|
| ① **空转** | 使用记录显示**连续 3 次** A 态建议均未被采纳 | 有受众但判据站不住 |
| ② **零运行** | 使用记录**无新增行**（§6.2 三态全含口径下） | **无受众** |

**撤回动作（两分支同）**：删除本工作流 + 收回 `sandbox/_parallel/README.md` §6 的触发导航
+ 移除 `CLAUDE.md` 与 Phase 0d-8 的指针 + **注销 Skill 入口 `parallel-session-check`**。

🔴 **② 为何必需（2026-09-17 补）**：原判据只有 ①，而它**预设 A 态记录存在**——静默从不运行
⇒ 永远攒不满 ① ⇒ 设施**既不证价值也不自我退役**。同族形态见 `retirement-completeness-audit` 记忆：
判据的证据窗口覆盖不到它的主要失败模式。实测触发本补丁：本工作流 2026-09-15 建成，至 2026-09-17
使用记录无新增行 ⇒ ① 在可见期内**不可达**。

🔴 **证据窗口改为三态全含**（见 §6.2）：原口径「每次输出 A 态后记一行」只记录成功分支，
使「**零运行**」与「**恒 B 态**」在证据面上**同形不可分辨**——同 `gate-validation-set-domain-coverage`：
验证集不覆盖被测对象的每个分支 ⇒ 恒绿且零信号。

🔴 **不以时间间隔判定**：「N 天无记录即撤回」属周期性提醒，`standards/06` §1 默认拒绝清单已拒
