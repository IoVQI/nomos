# 工作流认知准则 — 如何读懂一个工作流

> 本准则约束「**读懂某个工作流**」这件事：问什么（§1）、怎么答（§2）、问题集如何生长（§3）。
> 它是**判断层**文件：不配脚本、不设闸门、不计数。
> 入口是 Skill `workflow-explain`（若你的项目有）；本准则提供它消费的问题集与取证纪律。
> 🔴 **本准则只增不改问题**。答案不在本文件——答案会随源文件腐烂，问题不会。

## §0 定位

| | 本准则 + `workflow-explain` | `workflow_index.md` | `workflow_usage_guide.md` |
|---|---|---|---|
| 回答 | **这个工作流内部在做什么、为什么** | 存在什么 | 该调哪个、如何串联 |
| 受众 | **用户** | AI（会话启动加载） | AI（编排决策时读） |
| 产物 | 对话中的解释（可选落盘） | 注册表 | 路由表 |

## §1 问题集（只增不改）

> **生长机制见 §3**。问题条目不带日期与提出者——问题本身是通用的，来源属于会话记录。

### A. 触发与边界

| # | 问题 |
|:--:|---|
| A1 | 它什么时候被触发？是自动、链编排、还是只能人工调用？ |
| A2 | 它**不会**做什么？（明确的非目标） |
| A3 | 跑之前需要什么前置条件？缺了会怎样？ |

### B. 磁盘影响（用户最关心的一类）

| # | 问题 |
|:--:|---|
| B1 | 跑完我的磁盘上**多出**哪些文件？**改了**哪些？**删了**哪些？ |
| B2 | 有没有**不可逆**操作（删除 / 覆盖 / git mv / push）？ |
| B3 | 哪些文件是**共享索引**（只允许单写者）？ |

### C. 关系与位置

| # | 问题 |
|:--:|---|
| C1 | 它和那几个「看起来很像」的工作流有什么区别？（重叠面在哪） |
| C2 | 谁消费它的产物？它消费谁？ |
| C3 | 它在链模板里是第几步？ |

### D. 结构与可维护性（面向「从哪里入手优化」）

| # | 问题 |
|:--:|---|
| D1 | 它的 Phase 是怎么切的？哪一段是承重的、哪一段是收尾？ |
| D2 | 它有哪些闸门？各自 FAIL 时怎么处置？ |
| D3 | 它身上有没有**已知的坑**（实证记录）？ |
| D4 | 如果我要改它，**动哪里最省事、哪里会连锁**？ |

## §2 取证纪律（回答时强制）

1. **回源，不复述**：每个答案必须给出 `文件:行号` 锚点。禁止凭文件名推测内容。
2. **区分三种陈述**：① 文件里**逐字写着**的（引原文）；② 从多处**推出**的（写明推理链）；
   ③ **文件没写**（明说「未记载」，不得填补）。
   —— 这条是本准则对抗「旧说明书失效」的核心手段：旧设施的死因正是**回答了生成者以为的问题**，
   且答案无从证伪。
3. **范围声明**：答案只覆盖**该工作流文件 + 其注册/消费点**。不得外推为「整个工作流体系都如此」。
4. **成本纪律**：只读、单次会话内完成、**不得扇出子代理**（高扇出会迅速放大成本，
   且对「读懂一个文件」没有增益）。
5. **不确定就说不确定**：发现文件之间**互相矛盾**时，如实记录矛盾本身 + 各自锚点，不替它们裁一个。
6. **取证命令须先自证有区分力**：凡**命令的输出将作为判定依据**（方案里的核验 / 终验命令、
   一次性的现场核查），先拿一个**已知正确态**跑一遍，确认它给得出**非平凡**值——
   能区分「对」与「错」。对任何输入都恒返回同一值（**恒 0 / 恒空 / 恒真**）的命令，
   与「真的检查过了」**同形**，它给出的 0 不是证据。
   高发面：同一个 pathspec / 同一个选项在**不同子命令**下语义不同，而两种写法看起来都「合法」。

   ```bash
   # ❌ 可疑：恒 0 —— 与「已清空 / 无此文件」同形
   $ some-cmd -- 'archive/**/*.ipynb' | wc -l
   0
   # ✅ 同一目标的正确写法：给出真值
   $ some-cmd --name-only -- archive | grep -c '\.ipynb$'
   1
   # 🔍 区分力探针：把「恒 0」的写法指到一个必然非空的目标上——仍得 0
   $ some-cmd -- '**' | wc -l
   0
   $ some-cmd --name-only | wc -l
   <非零，现场取>
   ```

   —— 判据：**「已知非空」的输入给出 0（或「已知为空」的输入给出非 0），即判该命令无区分力**，
   换命令后重新取证。承重的是 0 与非 0 的**对照**；不要抄写会随提交漂移的读数，现场跑一次即可。

   > **分工**：本条管**一次性取证命令**是否有区分力；**闸门判据**的那一类问题另见
   > [`06 §3.1 ③`](06_改进与维护宗旨.md)——**范围以 06 为唯一真源，不在此复述**。

## §3 问题集的生长机制

**不许先验编写问题集**——先验问题集就是「生成者以为的问题」，正是旧说明书的死因。

生长循环：

1. Skill 作答后，**反问用户**：「读下来你还有哪卡住 / 想追问什么？」
2. 收集用户的**真实提问** → 判断是否属于**通用**问题（换个工作流也成立）。
3. 属于通用 → **提议**新增为 §1 条目 → **用户确认后**写入。
4. 回到 1。

**退出信号**：用户显式说「不用了 / 够了」。未收到该信号前不自行收口。

> 为什么强制这一步：问题集的增量主要来自「读者提问 → 补丁」，审阅纠错只是少数；
> **把真实疑问变成条目，才是常态化产出的真正来源**。

## §4 与既有设施的关系（一进一出）

本准则接手两类旧设施的职能位置（均零活跃消费者）：

| 旧设施 | 原职能 | 本准则如何接手 |
|---|---|---|
| 批量生成工作流说明文档 | 生成静态说明书 | 改**按需问答**（不批量生成文档；答案会腐烂，问题不会） |
| 维护工作流参考手册 | 手工维护手册 | 手册形态整体废弃，不再重建 |

⚠️ **不声称替代**工作流审计类设施——它们是**审计族**，职能不同。

## §5 退役判据（依 06 §2-5 退役对称性）

出现以下任一情形，本准则 + Skill 即应退役：

1. **连续 3 次**调用后，追问环节**从未产生过**新条目 ⇒ 问题集已饱和，准则退化为静态清单 →
   降级为 `workflow_usage_guide.md` 的一节，删除 Skill；
2. 用户不再主动调用（如连续一个季度零调用）⇒ 无实际受众；
3. `workflow_usage_guide.md` 或 `workflow_index.md` 扩展出单工作流的解释能力 ⇒ 本设施被既有设施覆盖。

退役执行时按 [`06 §2-5`](06_改进与维护宗旨.md) 的残留核查清单逐层执行
（🔴 **层数与各层检索手段以 06 §2-5 为唯一真源，不在此复述**）。
