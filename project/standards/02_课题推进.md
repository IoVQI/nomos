# 课题推进 — 从一页纸计划到投稿迭代

> 选题确认后的推进框架，配套笔记：[研究选题逻辑](01_研究选题逻辑.md)。
> 核心原则：**把大问题拆成可验证的小问题，快速迭代，尽早暴露风险，而不是按线性计划一口气做完。**

很多课题推进不下去，不是因为方向不对，而是因为"验证得太晚"：方法设计了很久，最后实验才发现根本走不通；或者做了大量实验，最后发现故事线不清晰。

适用于计算、数值、机器学习、工程建模等方向，其他方向也可参考。

## 阶段总览

| 阶段 | 主题 | 周期 | 产出 |
|:---:|------|:---:|------|
| 0 | 把选题写成"一页纸计划" | — | 一页纸计划（问题/不足/核心想法/假设/成功标准/边界） |
| 1 | 问题边界与成功标准冻结 | 1—2 周 | 一页纸计划定稿 + 实验协议初稿 |
| 2 | 深挖文献与锁定基线 | 2—4 周 | 相关工作对比表 + 基线复现结果 + 改进切入点 |
| 3 | **方法设计与最小可行验证** | 2—6 周 | 最小可行方法 + 初步实验结果 + 优化方向 |
| 4 | 完整实验与主结果 | 4—8 周 | 完整实验代码 + 主结果表/图 + 可复现脚本 |
| 5 | 消融、鲁棒性与深度分析 | 3—6 周 | 消融表 + 敏感性图 + 失败案例 + 讨论素材 |
| 6 | 论文写作与故事线构建 | 与实验同步 | 论文草稿 + 图表初版 + 修改意见列表 |
| 7 | 投稿前检查与迭代 | — | 投稿材料就绪 + 审稿修改计划 |

## 阶段 0：把选题写成"一页纸计划"

不要只停留在口头想法。动手写一页纸，包含：

- **研究问题**：一句话说明要解决什么问题。
- **现有方法的不足**：为什么现有方法不行？
- **你的核心想法**：用什么机制/思路来改进？
- **假设**：你认为什么条件下会有效？
- **成功标准**：做到什么程度算成功？例如：在某数据集上指标提升 X%，或计算成本降低 X%，或理论误差界更紧。
- **不做的事情**：明确边界，避免无限扩展。

> 💡 这一步的目的是：**让你和导师/合作者对"什么是完成"有一致预期。**

## 阶段 1：问题边界与成功标准冻结（1—2 周）

**目标**：把模糊想法变成可验证的研究问题。

### 关键动作

1. **明确输入、输出、条件**
   - 输入是什么？数据、参数、环境？
   - 输出是什么？预测、决策、理论界？
   - 在什么约束下研究？数据量、算力、实时性？
2. **定义评价指标**
   - 主要指标是什么？
   - 辅助指标是什么？
   - 如何衡量"更好"？统计显著性？误差棒？
3. **确定对比基线**
   - 必须对比哪些方法？
   - 是否已有公开实现？
   - 如果没有，是否要自己复现？
4. **设定失败判据**
   - 如果出现什么结果，说明这条路走不通？
   - 例如：在 toy problem 上都没有提升，就放弃该方向。

### 产出

- 一页纸计划定稿；
- 实验协议初稿：数据集、指标、基线、超参数搜索方式。

---

## 阶段 2：深挖文献与锁定基线（2—4 周）

**目标**：确保你不是重复造轮子，且你的对比是公平的。

### 关键动作

1. **锁定 5—10 篇最相关核心文献**
   - 包括：最经典方法、当前最强方法、与你想做的机制最接近的方法。
   - 用表格整理：方法、核心思想、数据集、指标、代码是否公开。
2. **复现关键基线**
   - 至少复现 1—2 个最重要的基线。
   - 尽量使用官方代码，记录环境、版本、随机种子。
   - 如果复现不出论文结果，记录下来，这本身可能就是一个发现。
3. **建立性能参考表**
   - 把已有文献报告的结果整理成表。
   - 标出哪些是论文报告，哪些是你复现得到的。
4. **找"缺口"**
   - 不是泛泛地说"现有方法不好"，而是具体到：
     - 在哪些数据分布下失效？
     - 在哪个模块上误差最大？
     - 计算瓶颈在哪一步？

### 产出

- 相关工作对比表；
- 基线代码与复现结果；
- 明确的"改进切入点"。

---

## 阶段 3：方法设计与最小可行验证（2—6 周）

**目标**：用最小代价验证你的核心想法是否成立。

这是最关键的阶段，建议遵循：

> **先做简化版，再逐步加复杂度。**

### 关键动作

1. **设计最小可行方法**
   - 只实现最核心的模块，其他部分用现成组件拼。
   - 例如：先在一个小数据集、小模型上验证。
   - 不要一开始就追求完整系统。
2. **设置"门槛实验"**
   - 如果你的核心机制有效，应该能在某个简单场景下看到明显信号。
   - 比如：损失下降更快、指标提升超过噪声水平、某个现象可复现。
3. **快速失败，快速调整**
   - 如果 1—2 周内没有任何积极信号，分析原因：
     - 实现有误？
     - 假设不成立？
     - 信号太小，需要更大规模？
   - 如果多次调整仍无效，考虑修改方法或缩小问题范围。
4. **记录所有尝试**
   - 包括失败参数、失败现象、代码版本。
   - 避免重复踩坑，也为论文中的"探索过程"提供素材。

### 产出

- 一个最小可行方法；
- 初步实验结果：有效/无效/部分有效；
- 下一步优化方向。

---

## 阶段 4：完整实验与主结果（4—8 周）

**目标**：把最小可行方法扩展成完整系统，得到可信的主结果。

### 关键动作

1. **搭建完整实验流水线**
   - 数据加载、预处理、训练、评估、可视化。
   - 确保可复现：固定随机种子、记录依赖版本、保存配置。
2. **实现多个基线和数据集**
   - 至少 2—3 个数据集或场景。
   - 每个数据集上至少 2—3 个强基线。
3. **公平比较**
   - 使用相同的训练/测试划分、超参数搜索预算。
   - 避免只调好自己的方法，不管基线。
4. **主结果表**
   - 生成论文级的主表：方法 × 数据集 × 指标。
   - 用均值±标准差，做显著性检验（如 t 检验、bootstrap）。
5. **可视化**
   - 关键曲线、收敛图、误差分布图。
   - 能一眼看出你的方法好在哪、差在哪。

### 产出

- 完整实验代码；
- 主结果表和图；
- 可复现实验脚本。

---

## 阶段 5：消融、鲁棒性与深度分析（3—6 周）

**目标**：证明你的方法为什么有效，以及边界在哪里。

### 关键动作

1. **消融实验**
   - 逐一去掉/替换你的核心模块，观察性能变化。
   - 回答：每个模块贡献多少？
2. **敏感性分析**
   - 关键超参数变化时，性能如何变化？
   - 对随机种子、初始化、噪声是否敏感？
3. **失败案例分析**
   - 找出你的方法在哪些样本/条件下失败。
   - 分析原因，这能提升论文深度，也能明确适用范围。
4. **理论或机制解释**
   - 如果可能，给出理论分析：收敛性、误差界、复杂度。
   - 或者通过可视化、统计检验提供直觉解释。
5. **与已有方法的深层次对比**
   - 不仅是指标对比，还可以对比：
     - 计算成本；
     - 内存占用；
     - 对数据量的依赖；
     - 在不同分布漂移下的表现。

### 产出

- 消融实验表；
- 敏感性分析图；
- 失败案例分析；
- 论文中的"讨论"部分素材。

## 阶段 6：论文写作与故事线构建（与实验同步进行）

**目标**：把技术工作转化为清晰、有说服力的论文。

### 关键动作

1. **尽早开始写作**
   - 不要等所有实验做完再写。
   - 方法部分可以在实现时同步写，实验部分每完成一组就写。
2. **先搭论文骨架**
   - 标题、摘要、引言、方法、实验、结论。
   - 用占位符填充未完成部分。
3. **明确故事线**
   - 问题是什么？为什么重要？
   - 现有方法为什么不够？
   - 你的核心洞察是什么？
   - 实验如何验证？
   - 贡献是什么？
4. **图表先行**
   - 先确定主图、主表，再围绕它们写文字。
   - 每张图要能说明一个关键点。
5. **内部评审**
   - 让导师、同行、师兄师姐读草稿。
   - 关注：逻辑是否连贯、贡献是否清晰、实验是否支持结论。

### 产出

- 论文草稿；
- 图表初版；
- 修改意见列表。

---

## 阶段 7：投稿前检查与迭代

**目标**：提高一次投稿的成功率，减少低级错误。

### 关键动作

1. **复现性检查**
   - 从零运行一遍代码，确保结果可复现。
   - 代码和数据是否准备好公开？
2. **对照期刊/会议要求**
   - 格式、页数、匿名要求、伦理声明。
3. **同行模拟评审**
   - 找 1—2 位了解领域的人模拟审稿。
   - 重点挑刺：创新性、实验充分性、写作清晰度。
4. **投稿后准备**
   - 根据审稿意见，制定修改计划。
   - 即使被拒，也要把意见用于改进。

## 推进中的管理原则

### 1. 每周设定可验证目标

不要写"继续做实验"，而是写：

- "本周完成基线 A 在数据集 B 上的复现，并记录结果。"
- "完成消融实验中的模块 C 移除测试。"

### 2. 保持研究日志

记录每天做了什么、遇到什么问题、下一步计划。
可以用 Notion、Obsidian、飞书文档等。

### 3. 设置止损点

提前想好：

- 如果 X 周内主指标没有达到 Y，就调整方向。
- 避免在一个方向上无限投入。

### 4. 与导师/合作者定期对齐

建议每 1—2 周同步一次：

- 已完成什么；
- 当前卡点；
- 下一步计划；
- 需要什么帮助。

### 5. 版本管理和实验追踪

代码用 Git，实验配置和结果用 MLflow、Weights & Biases 或简单 CSV 记录。
避免"忘了哪个参数跑出最好结果"。

## 常见坑与应对

| 常见坑 | 应对 |
|------|------|
| 方法设计太久，迟迟不做实验 | 先做最小可行验证，用简单实验证伪 |
| 只调自己的方法，基线用默认参数 | 给基线相同的调参预算 |
| 实验做很多，但故事线不清楚 | 先写引言和贡献列表，再补实验 |
| 失败结果不记录 | 所有尝试都记录，失败也有用 |
| 完美主义，一直不投稿 | 先投会议/快报，获取反馈 |
| 文献越读越多，导致方向漂移 | 以"一页纸计划"为准，新文献只补充，不改主线 |

---

## 总结

选题确认后的推进逻辑，可以概括为：

> **冻结问题 → 锁定基线 → 最小验证 → 完整实验 → 深度分析 → 同步写作 → 投稿迭代。**

其中最重要的是**阶段 3 的最小可行验证**。
如果这个阶段能尽早证明你的核心想法有效，后面就是工程和写作问题；如果证明无效，也能及时止损，换一个更可行的变体。

不要追求一次做出完美系统，而是追求**每一步都能产生可验证的反馈**。
