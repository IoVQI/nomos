# 闭环本会话

按顺序执行下列收尾动作。**每一步先判定是否适用**（判据写在步内），不适用就跳过并**说明理由**。

> 📌 **本文件是操作清单，不是规则真源**。每条规则的真源都在下面各自指向的文件里；
> 本文件与真源冲突时**以真源为准**，并顺手修正本文件。
>
> 🔴 **本指令是会话末的唯一路径**。会话收尾**不经过**任何编排工作流。

- **辅助会话**（任务由他会话指派）：**只做三件事**——① 更新自己的 claim（状态 + 逐条结项依据：

## 3. 记忆沉淀

**判据**：先过三道闸门——**触发 × 排除 × 确认**。

| 闸门 | 判据 |
|------|------|
| **触发** | 方法论 / 踩过的坑 / 用户明确认可的做法 |
| **排除** | 仓库已记录的、一次性的、常识 → **不写** |
| **确认** | 判别后**向用户确认**再写 |

**写什么**：一条记忆 = 一个事实，带 frontmatter（`name` / `description` / `metadata.type`）。
写得像给人看，不像给检索器看；相关记忆用 `[[other-name]]` 互链。
**别存仓库已经写了的东西。**

**写哪里**：Claude Code 的 project memory 目录。该目录由 cwd 派生，**源机与目标机不同，
勿手拼 slug** —— 用工具自动探测：

```bash
python ai_system/validation/check_memory.py --append-line <slug> --line-file <路径>
```

🔴 **必须走这个工具**，不要用编辑器手写插行：它按**字节**、**保持原行尾**、带幂等守卫，
并带**容量闸门**（本次写入若把索引推过 harness 读上限即 ABORT——越限后超出部分会在每次加载时
被静默丢弃）。

## 4. 交接提示词

**判据**：有**未完成工作要移交**，或用户显式要求。

> 🔴 **输出要求**：本节**开头先给一行判定**——「新提示词 N 个（路径…）」或「无（理由：…）」。
> **边界**：「已在报告 / 索引登记」**≠**「无需操作入口」——凡是**下一个会话必须执行**的剩余工作
> （含等待用户放行、需要设计决策的），其操作入口就是提示词。

1. 落 `coordination/handoff/active/<YYYY-MM-DD>_<task_slug>.md`
   （骨架四要素与复述纪律见 `coordination/handoff/README.md` §4/§5）
2. 文件头记**现场取的生成时间 + 生成时 HEAD commit**
3. **同批**在 `coordination/handoff/index.md` 登记
4. **本会话消费掉的提示词** → 移入 `consumed/`，索引状态改「已消费」并注明会话与结果
   —— 别让它挂在 `active/` 里冒充待办

⚠️ 提示词是**操作入口，不是事实真源**：复述的事实必须带来源锚点。

## 5. 并行启动建议

**判据**：会话结束时仍有**可分派**的剩余工作。

读 `ai_system/workflows/parallel_session_launch_workflow.md`，给出**三态之一**：

| 态 | 输出 |
|---|---|
| 建议并行 N 路 | 拓扑 + 各路写入域 + 预填 `coordination/_aux_session_prompt_template.md` |
| 不必并行 | **写明命中哪条判据** |
| 先澄清 | 写明缺什么信息 |

🔴 **三态都要留痕**：在 `coordination/_aux_session_prompt_template.md` §使用记录追加一行。
只记「建议并行」会让「零运行」与「恒不必并行」在证据面上同形不可分辨。

## 6. commit 提议（强制）

**判据**：`git status --porcelain` 非空。

1. 列出变更文件清单 + 拟用的完整 commit message，**等用户确认**
2. 确认后：**从 `git status --porcelain` 输出里取精确路径**，逐文件 `git add <精确路径>`
   —— 🔴 **禁用 `git add -A`**（防吞并行会话的未关联变更）
3. **提交前复核** `git diff --cached --name-only` 逐条确认；发现他会话文件 →
   `git restore --staged <path>` 再提交
4. **并行会话在场时**带 pathspec 提交；`git rm --cached` 类**不带** pathspec
5. 用户拒绝 → 跳过，并告知文件仍在工作区、不受版本保护

完整协议（含 pathspec / `--cached` 子类的机理与恢复配方）：`CLAUDE.md` §十 与
`coordination/claims/README.md` §3 铁律 4。

⚠️ **等待提交期间不要把文件留在 index 里**——他会话的无路径 `git commit` 会把它卷走。

## 7. 提交后状态复核 → clear 就绪结论

**判据**：§6 已执行完毕（提交完成，或用户显式拒绝提交）。

> 🔴 **为什么放在闭环内而不是叫「clear 前检查」**：`/clear` 由**用户自行执行**，本文件在那个时刻
> **触发不到**。把它定义为「闭环的最后一步产出『可安全 clear』的结论」，它才是**可执行**的。

1. 跑 `git status --porcelain`，把余下条目**分三类**列给用户：

   | 类别 | 判定 | 处置 |
   |---|---|---|
   | **本会话遗留** | 本会话产生、尚未提交 | 🔴 回到 §6；确实不提交的须**写明理由** |
   | **他会话在途** | 属其他会话的未提交改动 | 只**登记**（路径 + 标注「非本会话」），**不触碰** |
   | **未跟踪产物** | 可再生/临时产物 | 判定去留并说明 |

2. **给出明确的 clear 就绪结论**（一句话，必须含**判断**，不能只罗列文件）：
   - 可安全 → `本会话产物均已入库（HEAD <hash>）；工作区另有 N 个他会话在途文件，clear 不影响它们`
   - 不建议 → `本会话仍有未提交项：<列出>，建议先处置再 clear`

🔴 **本步不阻断 clear**：clear 是用户的决定，文件在磁盘上不受影响。
本步的职责是**让用户带着信息决定**，不是替用户决定。
